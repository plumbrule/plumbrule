# 维护准绳

这个仓库用同一份源文件（`rules/*.yaml`）生成三样东西：网站、`plumbrule` 技能和 npm 安装包。所以维护时只改源文件，不改生成物（`dist/`、`cli/skill/` 都不入库）。

开始前先读 `docs/编写指南.md`，里面写了硬约束的标准、数字、选型、来源这些细则；本技能只讲流程，不重复细则。

## 总规矩

- **每一步都跑 `pnpm check`，必须通过。** 它会检查格式、编号、引用、软措辞、编号台账、版本号和侧栏分组。
- **编号是公开的固定链接。** 已发布的编号不能改、不能删、不能复用。新规则一律在本主题里续编最大号 +1。
- **一事一处。** 动手前先查 `rules/_归属.yaml`，事情归别的主题管，就去那个主题改，本主题只留 `see` 引用。
- **没核实的不写成规则。** 写进该主题的 `open_questions`。
- **改完写更新记录。** 每次有实质改动，都在 `src/content/docs/changelog.md` 顶部「## 下一个版本号（未发布）」一节记一行，写明编号和改了什么。这一节没有就新建。
- **提交只加明确的路径。** 不用 `git add -A`。仓库根目录的 `prompt_research_*.md`、`*调研报告.md`、`*调研结果.md` 是个人文件，不提交。

## 场景一：修改一条规则

1. 用 `grep -rn "<编号>" rules/` 找到规则，并查有哪些地方引用了它。
2. 修改。如果要改级别（hard ↔ soft），按编写指南「硬约束还是软指导」的三条重新判断，拿不准就标 soft。
3. 规则的意思变了，比如要求变严、变松或换了推荐工具，在更新记录里写清楚。只是改错字或换说法的，不用记。
4. 依据变了的，同步改 `sources`，`checked` 写今天的日期。
5. 运行 `pnpm check`。

## 场景二：新增一条规则

1. 查 `_归属.yaml`，确认归哪个主题。
2. 查有没有重复：`grep -rn "<关键词>" rules/`。已有相近规则的，优先改那一条。
3. 编号：本主题现有最大号 +1。不能用 `_编号台账.yaml`「已废弃」里的编号。
4. 必填字段：`id`、`title`（祈使句，一句话）、`level`、`check`、`how`（具体工具、命令或审查点）、`applies`（只用 `_词表.yaml` 里的值）、`why`。按需填 `detail`、`ref_value`、`sources`、`see`。
5. 新来源加进本主题的 `sources`，编号续排，填 `date` 和 `checked`。
6. 运行 `pnpm check`，然后写更新记录。

## 场景三：删除、合并或废弃规则

已发布的编号不能直接删，否则 `pnpm check` 会报错。

1. 从主题文件里删掉这条规则。
2. 在 `rules/_编号台账.yaml` 的「已废弃」下登记，写明版本、改用哪条、原因。版本写下一个版本号；没有替代规则时，改用写 `[]`：
   ```yaml
   已废弃:
     COD-017: { 版本: 0.2.0, 改用: [COD-041], 原因: 与 COD-041 合并 }
   ```
3. 用 `grep -rn "<编号>" rules/` 找出其他规则 `see` 里对它的引用，改成新编号或删掉。
4. 运行 `pnpm check`，然后写更新记录。

## 场景四：新增一个主题

1. 在 `rules/_归属.yaml` 的「主题」下加一项：编号续排，`slug` 用小写短横线，`前缀` 用大写，不能和已有的重复。如果要从别的主题接管某类事，同时改归属，并通知那个主题删掉对应内容、改成 `see`。
2. 新建 `rules/NN-slug.yaml`，照 `rules/23-agents.yaml` 的结构写，`status: draft`，填 `reviewed_on` 和 `next_review`。
3. 在 `tools/lib.ts` 的 `topicGroups` 里把它放进一个分组。漏了 `pnpm check` 会报错。
4. 运行 `pnpm check`，再用 `pnpm dev` 本地打开 `/topics/<slug>/` 看一眼。
5. 写更新记录。

## 场景五：吸收补充调研结果

调研结果放在仓库根目录，是个人文件，不提交。它们**只作参考**：

1. 逐条对照现有规则，分成三类：
   - 支持现状；
   - 要改规则，包括说法过时、工具停更、许可证变了；
   - 不适用，写明原因。
2. 先把对照结果给维护者看，确认后再改。
3. 关键说法要找到原始出处（官方文档、标准、项目仓库）并加进 `sources`。只有调研报告一个出处的，写进 `open_questions`，不写成规则。
4. 改动按场景一到场景三做；更新记录里注明「据补充调研」。

## 场景六：定期复核主题

1. 找出到期的主题：
   ```sh
   grep -H "^next_review:" rules/[0-9]*.yaml | sort -t: -k3
   ```
2. 对每个到期主题：
   - 抽查来源链接还在不在、内容变没变；
   - 推荐的工具有没有停更、改许可证；
   - 版本或政策有没有到期；
   - 处理 `open_questions` 里能核实的项。
3. 改完把 `reviewed_on` 改成今天，`next_review` 往后推。默认推 6 个月；变化快的主题（Agent、大模型、安全、移动端）推 3 个月。
4. 只有经过一个没参与编写的人或 Agent 独立复核，`status` 才能从 `draft` 改成 `reviewed`。

## 场景七：发布新版本

1. 确认更新记录顶部有「## 新版本号（未发布）」这一节，内容写全。版本号这样定：
   - 只有修正和小补充，升修订号（0.1.0 → 0.1.1）；
   - 新增或废弃规则、新增主题，升次版本号（0.1.x → 0.2.0）。
2. 运行 `pnpm release <新版本号>`。它会做这些事：
   - 检查版本号和更新记录；
   - 统一两处版本号，把「未发布」换成今天的日期；
   - 更新编号台账；
   - 构建网站，打包 npm 包。
3. 提交，提交命令按脚本最后打印的来。
4. **下面三步要先问维护者，得到同意后再做。** 它们都会对外公开：
   - 部署网站：`pnpm run deploy`。注意不是 `pnpm deploy`，那是 pnpm 自带的另一个命令。
   - 发布 npm：
     ```sh
     cd dist && npm publish plumbrule-<版本>.tgz --access public
     ```
     这一步要维护者本人做两步验证，建议让维护者自己在终端里运行。发布后新版本会先进入待批准状态，要到 npmjs.com 上批准才会上架。
   - 推送代码和标签：
     ```sh
     git tag -a v<版本> -m "准绳 <版本>" && git push && git push origin v<版本>
     ```
5. 验证：
   - 网站：`curl -sI https://plumbrule.dev/` 能打开，`/install/` 页上显示的是新版本号；
   - npm：`npm view plumbrule version --registry=https://registry.npmjs.org/` 是新版本；
   - 安装：在空目录里跑 `npx plumbrule@<版本> install --dir <临时目录>`，能装上。

## 常见报错

| `pnpm check` 的提示 | 怎么处理 |
|---|---|
| 已经发布过，不能直接删除 | 按场景三，在编号台账里登记「已废弃」 |
| 这个编号已废弃，不能再用 | 换一个新编号：本主题最大号 +1 |
| 引用的规则 X 不存在 | 把 `see` 改成替代规则，或删掉这条引用 |
| 没有放进 topicGroups 的任何分组 | 按场景四第 3 步，加进 `tools/lib.ts` |
| 版本与 cli/package.json 不一致 | 不要手改版本号，用 `pnpm release` |
| 硬约束标题含软措辞 | 改成明确的要求，或者改标 soft |
| 来源 Sxx 从未被引用 | 删掉这个来源，或者在规则里引用它 |
