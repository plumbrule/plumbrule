# 编写指南

写或修改 `rules/NN-slug.yaml` 时照这里做。样板：`rules/23-agents.yaml`。

## 基本要求

- **通用。** 规范面向任何项目，不写某个具体产品、公司或平台的内部概念。例子用中性的（「订单服务」「示例仓库」）。
- **说人话。** 中文，短句；术语第一次出现时顺带解释。标题用祈使句，一句话说清要做什么。
- **只写结论。** 不搬调研报告原文，不写「报告认为」「我们」。
- **不写版本号。** 规则和选型里不写具体版本，只在官方明确规定最低版本时写（如「需要 2.1.277 及以后」）。版本单独记账。
- **一事一处。** 查 `rules/_归属.yaml`：归别的主题管的事，只留一句话并用 `see` 引用。
- **词表统一。** 级别、检查方式、适用范围、优先级、状态名、事故等级只用 `rules/_词表.yaml` 里的值。

## 硬约束还是软指导

标 `hard` 必须同时满足：

1. 有可靠出处（标准、官方文档、公认安全底线），或违反后果严重且公认；
2. 写得出检查方法（`how`）：自动工具，或明确的人工审查点；
3. 标题里没有「尽量」「可行时」这类软措辞；有适用前提的，前提写进标题。

否则标 `soft`。拿不准时标 `soft`。

检查方式：`auto` 工具能直接判定；`semi` 工具找候选、人确认；`manual` 只能靠评审或演练记录。

## 数字

规则里的数字（阈值、时长、比例）：

- 有官方出处的，引用来源；
- 没有出处但有道理的，写进 `ref_value`，说明是参考值和理由；
- 没有出处也说不出理由的，删掉。

## 选型（choices）

- 每个类别给一个默认推荐（`pick`），备选写清何时用，不推荐的写清原因。
- 优先推荐成熟的现成库或工具，不推荐自己造。
- 许可证写进 `license`，以项目官方仓库的 LICENSE 为准；没核实的写进 `open_questions`。
- 区分「独立运行的工具」（如 CI 里跑的扫描器）和「集成进产品分发的组件」，许可证要求不同（口径见 27）。

## 来源（sources）

- 只列被规则或选型引用的来源，不重复，同一链接只列一次。
- 优先官方文档、标准、法规原文；社区文章标 `community`，单个公司的经验标 `case`。
- `date` 是发布日期，不详写 `null`；`checked` 是核实日期。
- 法规类主题设 `legal_notice: true`。

## 待确认（open_questions）

没核实的关键说法、版本或政策日期、需要补调研的缺口，都写在这里。网站会显示为「待确认」，不要把没核实的内容写成规则。

## 英文版

- 英文版在 `rules/en/`，文件名、结构、编号、`level`、`check`、`applies`、`sources`、`see` 必须与中文版完全一致；只翻译给人看的文字。
- 改中文规则时同步改英文版，运行 `pnpm check` 会校验英文版是否完整、有没有残留中文。
- 英文版用 `rules/en/_词表.yaml` 和 `rules/en/_归属.yaml`，术语按这两份文件统一。

## 自检

改完运行 `pnpm check`，必须通过。
